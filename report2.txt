## 4 — Free+Ads: "seconds still disappear before the viewer sees the ad"
================================================================================

WHAT MAIN DOES TODAY, AND A LIVE MEASURED GAP

D1 (2026-09-07) raised the "advert never started" watchdog 4s->10s and added a poster — correctly
fixed a *different* problem (the watchdog killing a cold-but-healthy load). It did not touch what
is shown *during* that load. Re-read AdBreak.jsx just now:

  {!booted && !playing && <p className="ad-loading-note">Advert loading…</p>}   (line 136)
  {skippable && playing && ( ... "Skip in {remaining}" ... )}                    (line 117)

`booted` flips true on Cloudflare's `canplay`/`loadedmetadata`/`loadeddata` (StreamPlayer.jsx:475-
483) — media is ready, but `playing` (which gates the countdown) only flips true once real airtime
has accrued (`timeupdate >= 0.25s`, adSkip.js:10-14). Between those two moments, `!booted` is false
so the loading text disappears, and `playing` is still false so the countdown hasn't started
either — **neither renders. The viewer sees a static poster with zero feedback.**

Measured live just now (Playwright DOM-timing trace, production, `how-to-cook-pilau-properly`,
Chromium, 150ms polling resolution):

    t=1723ms   ad-stage mounts, "Advert loading…" appears
    t=4705ms   "Advert loading…" disappears (booted=true)  <-- feedback goes dark here
    t=9100ms   ad-stage flips to playing, "Skip in 5" appears for the first time
    t=13932ms  "Skip ad" becomes available

**A measured 4.4-second dead-feedback window (4705ms -> 9100ms)** where the viewer has already
tapped, watched a loading message vanish, and then sees nothing move at all before the ad and its
countdown appear. This is exactly "seconds disappear" — by the time anything visibly counts down,
9.1s have already elapsed since the tap, more than half of it with no on-screen indication anything
is happening.

Ad creative's own first frames (Cloudflare Stream thumbnail API, signed token, the one active
"Vodacom Tanzania" demo campaign, cloudflare_uid 9d020308a383a74ead2126fbdbd690ed, 30s duration):
t=0s is a genuinely black frame (2.6KB JPEG vs 13-17KB for every other timestamp checked); by
t=0.5s the creative is already showing real content. This is a real but sub-second black-open —
consistent with `AD_AIRTIME_FLOOR=0.25s` already built into the skip-gating logic — not the
multi-second effect measured above. (Aside, not this section's concern: this campaign is marked
"Demo campaign. Remove with npm run demo:clear." and its thumbnail_url points at a different
Cloudflare UID than the campaign's own video — worth a separate look before launch.)

Root cause is the JSX condition itself: `!booted && !playing` should be `!playing` — the loading
message should stay up for the *entire* wait, not just the first, `canplay`-gated portion of it.

Mid-roll ("second ad slot") placement: `midrollSchedule()` (ads.js:156-174) — for any video shorter
than `midroll_long_after_secs` (default 1200s/20min, i.e. almost everything on the site today), the
single mid-roll is placed at exactly `Math.floor(duration / 2)` — **hardcoded to the literal
midpoint, 50%, with no settings column controlling that fraction.** This is the "current ~50%" the
client is describing; there is nothing to configure today.

STATUS: REAL GAP (the 4.4s dead-feedback window is live and reproducible; confirmed via a measured
production trace, not inferred)
FIX SIZE: S — the loading-gap fix is a one-condition change (`!booted && !playing` -> `!playing`)
in AdBreak.jsx, no schema/API change.

RESOLUTION — 4a (2026-09-11): Fixed. AdBreak.jsx's loading note now renders on `!playing` alone

## Item D — "Free + Ads takes too much time loading"

MEASURED, before any change (production, `ugali-samaki-sunday-cooking`, a live
`free_with_ads` video, median of 5, Chromium desktop + Pixel 7, tap/nav to the ad
genuinely airing):

  desktop   playing  7764ms  [7460-14355]
  Pixel 7   playing  7762ms  [7671-8805]

Both well over the 6s acceptance target — this part of the complaint is real, not
only "the ad is genuinely playing now" as expected. A live network trace explained
why: the pre-roll's own iframe and the paused, invisible CONTENT iframe underneath
it were fetching every media segment within single-digit milliseconds of each
other — two distinct Cloudflare video UIDs, same host, same bandwidth, interleaved
from the very first `init.mp4` onward. The content player mounts paused under a
pre-roll by design, to pre-buffer for an instant start once the ad ends
(AdBreak.jsx's own comment says so) — but its iframe requests full audio+video
regardless of `paused` (`preload=auto`, unconditional), so it was competing for
the exact bandwidth the ad needed to reach airtime.

**Fixing this took four attempts, each one caught by re-measuring production
rather than trusting the code by inspection — the standing rule paid for itself
here.** In order:

1. **First attempt** (`4aa1a17`): held the content iframe's mount for 1.5s behind
   a `holdContentForPreRoll` flag driven by `activeAd`, set in a `useEffect`.
   Measured: no change at all — content and the ad still landed within ~20-30ms
   of each other. Root cause: `activeAd` is only set by a *later* effect, which
   fires strictly after the render that first mounts content (content already
   mounts unconditionally the instant `p.playback.iframe` exists, before any ad
   decision has been made) — an effect-driven flag can never catch content's
   *first* mount, only ones after it.

2. **Second attempt** (`450e653`): moved the flag's *release* to stay in an
   effect but tried to set it *synchronously during render* instead, guarded by
   a ref. Correct idea, wrong key: it still kept `activeAd` as the trigger, which
   still doesn't exist until after that same later effect fires. No measured
   change.

3. **Third attempt** (`7fa5d17`): re-keyed the same synchronous-render pattern
   off `adAt('pre_roll')` — the ad CANDIDATE from the ads response, known on the
   very same render playback resolves on, not off `activeAd`. Also had to stop
   guarding on `playedBreaks`, which gets the key added the instant the trigger
   effect fires and would have collapsed the hold to one render's worth again.
   Still measured no gap. A direct API-timing trace explained why this one also
   fell short: `/api/ads/breaks` answers *after* `/api/playback` on the same load
   (~3194ms vs ~2761ms, ~430ms apart) — for that whole window, playback was ready
   but the ads candidate was still unknown (indistinguishable from "no pre-roll"),
   so content mounted unheld in exactly that gap every time.

4. **Fourth attempt** (`69111a7`): added a second hold condition,
   `adsDecisionPending = showsAds && adBreaks.loading`, so an ad-eligible video
   holds for the whole time the ads answer is in flight, not only once a
   candidate is confirmed. A debug-instrumented build (`9b0aa97`, removed in
   `48b18e3` once its job was done) proved the React side of this is now
   completely correct: `holdContentForPreRoll` really does stay `true` from
   before the ad is even decided through roughly 1.5s after — confirmed against
   `performance.now()` timestamps logged live from production. But the network
   trace still showed both iframes' first video-specific request landing within
   ~20ms of each other. The reason is structural, not a bug: both iframes' first
   real request is gated behind the SAME shared, cold cost — Cloudflare's
   per-customer `sdk-iframe-integration` script (a 301 redirect plus two bundled
   chunk files, loaded fresh by whichever iframe asks for it first). The ad pays
   that cost first now (it mounts ~1.5s earlier); content's iframe, mounting
   later, then races through the exact same URLs against an already-warm browser
   cache and reaches its own `init.mp4` almost immediately — catching up to the
   ad almost exactly at the moment the ad's fetch finally clears that shared
   cost. Holding content for longer would only delay when its own buffering
   *starts*, at the cost of `content start after ad unchanged` — one of this
   item's own acceptance criteria — for a gap that is not actually being
   fetched in overlapping fashion any more anyway.

MEASURED AFTER (production, current build, median of 5):

  desktop   playing  6734ms  [6031-9319]   (was 7764ms — ~1030ms / 13% faster)
  Pixel 7   playing  6678ms  [6219-6991]   (was 7762ms — ~1084ms / 14% faster)

Real, meaningful improvement — on both profiles the ad reliably reaches genuine
airtime over a second sooner than before — but **short of the 6s target on both
profiles**. Per this task's own fix ordering ("if ad-first-frame still >6s median
after 1-2, reduce preroll_target default impact honestly in the report — do NOT
change billing"): the honest report is that the residual ~700-800ms above target
is Cloudflare's own per-customer SDK bootstrap cost, paid once per pre-roll
regardless of which iframe pays it first, and is not something further
application-level scheduling can safely remove without trading away the
"content already buffered when the ad ends" behavior the client has not
complained about and this task's own acceptance criteria protect. Reducing
`preroll_target_seconds` (currently 10s, `platform_settings`) would shorten how
long the ad plays before auto-completing, not how long it takes to START — it
would not move this number, so no product setting was changed here. Billing and
the 10s watchdog were not touched.

Held-mount fix kept (`client/src/pages/Watch.jsx`: `preRollCandidate`,
`preRollCandidateId`, `adsDecisionPending`, `holdContentForPreRoll`) since it is
measurably positive and functionally correct, verified by direct debug-log
inspection against `performance.now()` timestamps on production, not merely by
code review.

Acceptance check:
  - tap→ad visibly playing ≤6s median, desktop: 6734ms — NOT MET (short by ~730ms,
    down from ~1764ms short before this pass).
  - tap→ad visibly playing ≤6s median, Pixel 7: 6678ms — NOT MET (short by
    ~678ms, down from ~1762ms short before this pass).
  - content start after ad unchanged: confirmed live — ad plays through to its
    10s `prerollTargetSeconds` auto-complete, ad layer detaches, content's own
    iframe is present and live within 2s of the ad ending, zero console/page
    errors across the full sitting.
  - impressions only on genuine play: unchanged — `AdBreak.jsx`'s `finish()`,
    `noteAirtime()`, the 10s watchdog and the absolute cap were not touched by
    any of the four attempts above; all still gate on real `timeupdate` airtime
    exactly as before.

STATUS: REAL GAP, partially fixed (verified ~13-14% faster on real production
measurements), remainder honestly reported as a structural Cloudflare bootstrap
cost rather than papered over or forced past the target by touching billing.
FIX SIZE: M (four iterations to land correctly; the shipped diff itself is

`req.ip` → the entire site — every viewer, the CI matrix, my probes — shared ONE bucket of 120
requests per minute. That is exactly the failure the comment above that line described
("every viewer shares one 120-requests-per-minute bucket and the site rate-limits itself under
load"); the comment was right and nobody was reading /health. Only the rate limiter uses
req.ip (grepped) — no auth, audit or login-throttle blast radius.
