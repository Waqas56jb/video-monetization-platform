## ISSUE 1 — Revenue split: Super Admin must control everything (client set 70/30; some pages still show 60/40)

### How the split actually flows through the code today

The split lives in one place: `platform_settings.creator_split_percent` (`server/src/db/migrations/001_core_schema.sql:273`, default `70`), with an optional per-creator override on `creator_profiles.revenue_split_percent` (`001_core_schema.sql:85`). All read/write access goes through `server/src/services/settings.js`:

- `getSettings()` (`settings.js:13-18`) — cached 60s, `select * from platform_settings where id = 1`.
- `updateSettings(patch)` (`settings.js:20-47`) — the only writer; `creator_split_percent` is in the `allowed` whitelist (`settings.js:22`); invalidates the cache on write.
- `splitPercentFor(creatorId)` (`settings.js:53-62`) — returns the creator's override if set, else the platform default, else a hardcoded literal `70` as a last-resort fallback (`settings.js:61`) — this fallback only fires if the settings row itself is somehow missing, not a normal code path.
- `applySplit(amountTzs, creatorPercent)` (`settings.js:65-68`) — pure math, rounds in the creator's favor.

Every place that calculates or displays a split was traced. All of them call through `settings.js` live — there is no separate hardcoded 60/40 anywhere in the *application* code:

### Do historical rows store their own split? Yes — and this is where the real 60/40 problem is

Both `purchases` and `earnings` snapshot the split **at the moment of the transaction**, in their own `split_percent` column:
- `purchases.split_percent` (`001_core_schema.sql:195`), alongside `creator_amount_tzs` / `platform_amount_tzs` (computed once, at settlement time, in `payments.service.js:41-42,57-70`).
- `earnings.split_percent` (`001_core_schema.sql:216`), alongside `creator_tzs` / `platform_tzs`.

This is deliberate and documented in the admin UI itself: `RevenueTab.jsx:15-17` — *"The global split applies to new sales only. Money already split stays split the way it was — changing the rule cannot reach backwards and quietly restate what a creator was told they had earned."* Migration `016_reconcile_earnings_ledger.sql` exists specifically to keep `earnings.purchase_id` correctly joined to its `purchases` row so this ledger stays reconcilable.

**A read-only production query shows this is not theoretical — it already happened:**

```
purchases.split_percent distribution:
  60  → 34 rows, first 2026-08-28T06:46:41Z, last 2026-09-02T01:53:19Z
  70  → 20 rows, first 2026-05-19T20:16:09Z, last 2026-08-23T03:03:24Z

earnings.split_percent distribution:
  60 / sale → 34 rows (2026-08-28 → 2026-09-02)
  60 / ad   →  3 rows (2026-08-27T02:40 → 2026-08-27T03:14)
  70 / sale → 21 rows (2026-05-19 → 2026-08-23)
  70 / ad   →  5 rows (2026-08-10 → 2026-08-21)
```

The live `platform_settings.creator_split_percent` was **not** 70 the whole time. Somewhere between 2026-08-23 and 2026-08-27 it was changed to **60** (40% platform), stayed there through at least 2026-09-02, and was changed back to 70 by 2026-09-04 06:09:54Z (the row's current `updated_at`). This matches `RAILWAY-MOVE.md:244`, a boot log captured during that window that literally prints `database connected · split 60/40` — independent confirmation this was the real live value at the time, not a demo artifact. There is no `staff_actions`/audit table in this schema that logs settings changes (confirmed: `select ... from staff_actions` errors, "relation does not exist"), so **there is no audit trail of who changed it or why** — only the ledger rows it left behind.

**Financial impact, quantified from production (read-only):**

- 34 purchases at 60/40 instead of 70/30: gross TZS 55,500 → creators were paid TZS 33,300; at 70/30 they should have received TZS 38,850 → **TZS 5,550 total shortfall** across 4 creator accounts.
  - Two are **real creator accounts**: `safarihostadventures@gmail.com` ("Tiger") — TZS 1,100 shortfall over 22 purchases; `yaschali@gmail.com` ("Yasmin Chali") — TZS 200 shortfall over 2 purchases. **Real-money underpayment: TZS 1,300.**
  - Two are demo/seed accounts (`demo.juma@mtonyo.demo`, `demo.asha@mtonyo.demo`) — TZS 4,250 of the total, not real money.
- 3 ad-impression earnings rows at 60/40: gross TZS 275 → paid TZS 165 vs TZS 193 at 70/30 — TZS 28 shortfall (negligible).

**What would/wouldn't reflect an admin change today, concretely:**

*Immediately reflects a live setting change* (reads `platform_settings`/`creator_profiles` on every call, no caching beyond the 60s TTL in `settings.js:5`): payment settlement (`payments.service.js:41`), ad-revenue split (`ads.js:215`), creator earnings API (`earnings.routes.js:80`), admin creator list/settings/revenue screens (`admin.routes.js:900-908,1162-1173`), stats endpoint (`stats.routes.js:47`), homepage Hero stat (`Hero.jsx:108`) and For Creators section (`ForCreators.jsx:18`), client Earnings tab (`EarningsTab.jsx:156`), admin CreatorsTab/RevenueTab/SettingsTab editors.

*Does NOT reflect it, by design or by omission:*
- Every already-recorded `purchases.split_percent` / `earnings.split_percent` row — frozen at settlement time (intentional, per `RevenueTab.jsx:15-17`).
- The historical donut charts — intentionally shows the mix of past earnings, not the current setting.
- **`client/src/data/copy.js:310`** — the "Generous 70/30 revenue split" marketing string is static text, never re-evaluated against `platform_settings`. The one unfixed hardcode.
- The `?? 70` UI fallback literals scattered through the frontend are not bugs — they only render before the API response lands — but during the recent 60/40 window they would have briefly shown "70" on first paint while the real API value was 60, a small but real inconsistency window on every page load.

### Discrepancy list (current, concrete)

1. **`client/src/data/copy.js:310`** — hardcoded "Generous 70/30 revenue split" marketing copy; will silently go stale the next time the setting changes. This is the only place in the *code* that doesn't read live.
2. **37 historical `earnings` rows + 34 `purchases` rows dated 2026-08-27/28 through 2026-09-02** are permanently recorded at 60/40 in the production database, disagreeing with the current (correct) 70/30 live setting — TZS 5,550 in creator-earnings shortfall baked into the ledger (TZS 1,300 of it on two real creator accounts), and no record of who changed the setting or why.

### Does the poster render at 0 ms on every entry path?

**No — only on internal navigation.** Two different "Step 2 shell" mechanisms exist, and only one has a poster ready at 0 ms:

1. **`WatchSkeleton`** (`client/src/components/watch/WatchSkeleton.jsx:8-42`) is used as the `Suspense` fallback for the lazy-loaded `Watch` chunk (`client/src/App.jsx:51-70`) and as Watch's own first paint while `/api/videos` is in flight (`client/src/pages/Watch.jsx:664-671`). It renders `<img class="watch-preview-poster">` **only if `thumb` is present** (`WatchSkeleton.jsx:20-22`); otherwise a bare grey `<div class="skeleton skeleton-player" />` (line 23) — no picture. `thumb` comes from router `state.preview`, populated **only by internal `<Link>` clicks** (`Explore.jsx:253`, `Trending.jsx:65`, `MoreLikeThis.jsx:55`, `ContinueWatching.jsx:53`, `LibraryTab.jsx:41`, `CreatorProfile.jsx:36,61,198`). **A direct URL load, a shared link, and a hard back-navigation all arrive with no `location.state`**, so `WatchSkeleton` renders the bare skeleton div, not a poster. Real gap: "poster must show immediately" is true for card-click navigation and false for direct URL / shared link / back-nav after a full reload.

2. Once `/api/videos/:slug` resolves but the playback iframe is not ready yet, **Watch.jsx's own boot block** shows a real poster from server data: `<img className="stream-poster" src={mediaUrl(v.thumbnailUrl)} />` (`Watch.jsx:814-822,864-877`). This covers every entry path equally (depends on the API response, not navigation type). Warm this typically lands in ~500-960 ms; on a cold Home the render-to-first-card can run 2.3–8.6 s (M2-GAP.md §1), so on a slow/cold load the grey no-picture skeleton can persist a non-trivial time before this second poster appears.

**New finding not in the cited docs — a black handoff between the two posters.** When `p?.playback?.iframe` becomes available, Watch.jsx's conditional chain (`Watch.jsx:812-891`) **swaps the boot block (with its poster `<img>`) for `<StreamPlayer>`**, which renders no poster at all — its markup is `<div class="stream-shell is-live"><iframe class="stream-frame" .../></div>` (`StreamPlayer.jsx:698-722`). `.stream-shell` has a plain solid `background:#000` (`client/src/styles/realdata.css:305`), and `.stream-frame` starts at `opacity:0`, only reaching `opacity:1` once `is-painted` is added on the iframe's own `onLoad` (`realdata.css:309-326`; `StreamPlayer.jsx:190,710-712`). So for the interval between "our poster is removed" and "the iframe's document has loaded and painted," the viewer sees solid black — a genuine, currently-live black-screen moment (roughly bounded by PLAYER-MEASURE.md's "iframe" column, ~930–1150 ms desktop, up to ~1.7–1.9 s on Fast 3G/portrait, though measured from tap rather than from the poster-swap instant).

**`buildSrc` does not set a `poster=` param, and this is deliberate, not an oversight.** `StreamPlayer.jsx:24-42`:
```
url.searchParams.set('autoplay', 'true')
url.searchParams.set('muted', 'true')
// Do not put a signed poster on this URL. It doubled the JWT, aborted the
// embed (net::ERR_ABORTED), and left the same dead Play overlay.
```
Tried and reverted — a signed poster URL doubled the JWT and broke the embed outright. So the real gap is not "add `poster=`" but "keep our own poster mounted through the swap into `StreamPlayer`" (e.g. render `v.thumbnailUrl` as a background layer inside/behind `StreamPlayer`'s own shell rather than only in Watch.jsx's boot block, so it survives the transition).

## ISSUE 3 — Preview control: no "half the video" rule


```
… possibly: await api.share.payload(slug)                          // await #2 (cold clip)
```

`downloadFile()` fetches the clip cross-origin, converts to a `blob:` URL, clicks a synthetic `<a download>`. This is the well-documented WebKit/iOS Safari limitation: **iOS/iPadOS Safari does not honour the `download` attribute** — it navigates/plays the resource in place instead of saving it, regardless of construction. macOS desktop Safari is not subject to this. Stated from established WebKit platform behaviour, not a test run in this audit — there is no existing e2e coverage for `saveClip`/`downloadFile` in this repo, and WebKit-in-Playwright cannot stand in for real Safari here any more than for video playback. Needs a real iPhone/iPad — the gap already named in CLIENT-REPORT.md §17.

## ISSUE 6 — Super Admin logo → public homepage

**What the logo currently does: nothing.** `admin/src/components/layout/Sidebar.jsx:97-103`:
```jsx
<div className="logo">
  <img className="logo-img" src="/logo-lockup.png" alt="MTONYO+" decoding="async" />
</div>
```
No `<Link>`, no `<a href>`, no `onClick`, no hidden handler, no `cursor:pointer`. Clicking the logo today does literally nothing.

**Cross-origin session safety.** The admin app and public client app are separate Vercel projects on separate origins. Browser storage (`localStorage`/`sessionStorage`) is partitioned per-origin by the browser itself — standard platform behavior, nothing in this codebase overrides it. Checked how the admin app holds its session, `admin/src/lib/api.js`: distinct key names (`mtonyo.admin.access`/`.refresh`) from the public app's own (`mtonyo.access`/`.refresh`), and **the session is durably persisted, not memory-only** — module-level variables initialize straight from `localStorage` at load, and `saveSession()` writes to both memory and storage ("Memory is the live session; localStorage is a backup").

So: navigating the admin tab to a different origin cannot clear or touch the admin origin's `localStorage` — basic same-origin-storage fact, true regardless of tab-vs-new-tab — and because the token persists in storage (not only in a JS variable that resets on reload), returning to the admin origin (Back, or a fresh tab) re-reads the token and the session is still there. **A same-tab navigation to the public site would not destroy the admin session.**

**Recommendation: `target="_blank"` (new tab) anyway.** Not because the session is at risk — it isn't — but a full-page navigation away from the admin SPA discards whatever in-app state the admin was mid-way through (an open tab, filters, an unsaved form), and there is zero cost to a new tab since the session persists independently of which tab is open. Wire it as `<a href="https://video-monetization-platform-chi.vercel.app/" target="_blank" rel="noopener noreferrer">` wrapping the existing logo `<div>`'s contents.

```

FIX SIZE: S
DEVICE-SPECIFIC: no
```

RESOLUTION (2026-09-06): `admin/src/components/layout/Sidebar.jsx`'s logo `<div>` is now an
`<a href={DEPLOY.publicApp} target="_blank" rel="noopener noreferrer">` (`DEPLOY.publicApp` from
the existing `admin/src/lib/deployUrls.js`, so the URL is not a second hard-coded literal). New tab,
per the report's own recommendation — not because the session was ever actually at risk (confirmed

## ISSUE 7 — Viewer/creator/sub-admin/Super Admin role separation

### How the client Dashboard is actually gated

`client/src/pages/Dashboard.jsx:21-50`:
```js
const ACCOUNT_TABS = ['analytics', 'profile', 'settings']
const CREATOR_TABS = ['overview', 'library', 'purchases', 'upload', 'videos', 'earnings']

const TABS_BY_ROLE = {
  viewer: ['library', 'purchases', 'become', ...ACCOUNT_TABS],
  creator: [...CREATOR_TABS, ...ACCOUNT_TABS],
  admin: [...CREATOR_TABS, ...ACCOUNT_TABS],
  sub_admin: ['library', 'purchases', ...ACCOUNT_TABS],
}
```
The tab actually shown is constrained to this `allowed` list; requesting an unlisted tab via `?tab=` renders a refusal panel (lines 198-208). **This part is correctly role-gated**: a pure viewer cannot reach `upload`/`videos`/`earnings` by URL, and a sub-admin cannot reach any creator-only tab either (fixed previously precisely because a sub-admin used to see four red error panels).

The `role` driving `TABS_BY_ROLE` is `panelRole` (`AuthContext.jsx:210`), computed by `client/src/lib/accountSide.js:14-22` (`panelRoleFor`) — this **is** side-aware, returning `'viewer'` when a dual-capability account has explicitly chosen the Watch/viewer side. Tab-level routing is correct and side-aware.

### The actual leak — distinct from CLIENT-REPORT.md section 7

CLIENT-REPORT.md §7 is entirely about **account creation** (Create signup silently creating a Watch account) and the **dashboard menu list**. It does not touch what renders *inside* a tab both sides share. That is a different, confirmed bug:

**1. `client/src/components/dashboard/tabs/ProfileTab.jsx:25`** — `const { isCreator } = useAuth()` gates Creator name/category/verified-note fields (lines 164-203) and the payout ("Getting paid") panel (lines 276-280). `isCreator` is `AuthContext.jsx:214`: `studioAccess = hasCreatorStudio(accountRole, creator) || Boolean(sides.creator)`. `hasCreatorStudio` (`accountSide.js:24-29`) is **not side-aware** — it only asks "does this account have creator capability at all," ignoring `accountSide`/`side` entirely:
```js
export function hasCreatorStudio(accountRole, creatorProfile) {
  const real = accountRole || 'viewer'
  return real === 'creator' || real === 'admin' || real === 'sub_admin' || Boolean(creatorProfile)
}
```

**2. `AnalyticsTab.jsx` — the same pattern, and it's server-driven, not just a client oversight.** `server/src/modules/account.routes.js:299-342`:
```js
router.get('/analytics', asyncHandler(async (req, res) => {
  const isCreator = await hasCreatorAccess(req.user)   // line 302
  ...
  if (!isCreator) return res.json({ role: 'viewer', viewer, creator: null })   // line 342
```
`hasCreatorAccess` (`server/src/middleware/auth.js:132-137`) is pure capability, with **no concept of which side the caller is currently browsing on** — no `side`/`accountSide` parameter anywhere in the request. So the server itself unconditionally returns full creator analytics (views, paid unlocks, conversion %, revenue chart) to any account with creator capability, even while deliberately on the Watch/viewer side.

**Why this is real:** `profiles.role` is a single, permanent column — once an account has creator access, `role='creator'` forever (`022_viewer_enabled.sql:1-3`: Watch/viewer-side is the separate `viewer_enabled` boolean, Create-side is the `creator_profiles` row). There is genuinely no server-side signal distinguishing "this dual-role account, right now on Watch" from "this dual-role account, right now on Create" — every capability check answers the same way regardless.

**Net effect:** a dual-role account, while on the viewer/Watch side, opening **Profile settings** or **My Activity (Analytics)** — both shared tabs reachable from either side — sees full creator-only content instead of the viewer-only view. Matches the client's complaint precisely: a shared component/route renders creator fields based on capability, not on which view is currently open.

**This is a display leak, not a security hole.** Checked whether a pure viewer could actually *change* payout details via the API: `account.routes.js:184` — `if (await hasCreatorAccess(req.user)) { ...update creator_profiles... }` — a caller with no creator capability has that block skipped entirely, so POSTing payout fields from a true viewer account silently changes nothing. The leak only manifests for accounts that legitimately hold both sides, and only as unwanted visibility, not writable access they shouldn't have.

### Dual-role switch/toggle

Only one exists, and it's not available to ordinary users: `Sidebar.jsx:202-216` — gated to `accountRole === 'admin' && isCreator`, i.e. only for platform administrators who also have a creator profile. A regular person who legitimately signed up on both Watch and Create has **no in-dashboard way to switch sides** — the only way is to sign out and log back in choosing the other option on the login screen's Watch/Create toggle. Because tab routing *is* side-aware, the two dashboards do not render simultaneously — the confusion is narrower than "both UIs at once": it's the two shared tabs (Profile, Analytics) leaking creator content into what should be a clean viewer-side view.

### Server-side role guards

`server/src/middleware/auth.js`: `requireRole(...)`, `requireStaff = requireRole('admin','sub_admin')`, `requireAdmin()` (explicitly refuses `sub_admin` too — "Sub-admins cannot view or change accounts"), `hasCreatorAccess()`/`requireCreator()`, `requirePermission(module)` (per-module grant checked against `staff_permissions` on every request).

**Existing tests — source-inspection only, not live 403 assertions.** `auth.import.test.js:13-19` and `creators.follow.import.test.js:27-43` both read the source as text and regex-assert guard calls appear — neither issues an HTTP request. No test in the repo actually calls a creator-only or payout-only route with a viewer-role token and asserts `403`. `smoke.js` does real HTTP calls but is a manual CLI script, not part of the automated suite. **This is untested, not confirmed broken** — the guard code exists and reads correctly, but no regression test would catch it if it stopped working.

### Sub-admin vs super-admin (as currently implemented)

Admin nav (`admin/src/components/layout/Sidebar.jsx:15-55`): `Users`, `Creators`, `Revenue & Splits` are `adminOnly: true`; everything else is gated per-module. Server side, sensitive mutating routes carry an **additional** `requireAdmin()` on top of `requirePermission()` (e.g. `admin.routes.js:833,867,898,914,939,1015,1274,1686` — comment: "because a sub-admin must not see or change them"), so a sub-admin is 403'd regardless of any permission grant. #### 1. Migration — `034_creator_capital.sql`

Highest existing migration is `033_watch_progress_hidden_at.sql` (note: there are two pre-existing `021_*` files — `021_share_card_cache.sql` and `021_crawler_hits.sql`, a numbering collision already in this repo, not to be repeated). **Next number: `034`.**

```sql
-- ============================================================================
-- 034 · Creator Capital — interface + manual workflow, no lending engine
--
-- MTONYO+ is not the lender. AirPay decides who is approved and for how much;
-- this table is where that decision, and the manual review that leads to it,
-- is recorded and shown back to the creator. Nothing here disburses money —
-- disbursement and collection are AirPay's system, reached outside this
-- platform. What lives here is: are they eligible to ask, did they ask, what
-- did AirPay/the admin decide, and where do they stand on repaying it.
-- ============================================================================

do $$ begin
  create type creator_capital_status as enum
    ('building', 'under_review', 'approved', 'active', 'repaid', 'declined', 'paused');
exception when duplicate_object then null; end $$;

create table if not exists creator_capital (
  id                 uuid primary key default gen_random_uuid(),
  creator_id         uuid not null references profiles(id) on delete cascade,
  status             creator_capital_status not null default 'building',

  months_required    smallint not null default 6 check (months_required > 0),

  approved_amount_tzs   integer check (approved_amount_tzs is null or approved_amount_tzs > 0),
  purpose               text,
  repayment_terms       text,
  amount_repaid_tzs     integer not null default 0 check (amount_repaid_tzs >= 0),
  remaining_balance_tzs integer generated always as
    (greatest(coalesce(approved_amount_tzs, 0) - amount_repaid_tzs, 0)) stored,

  next_review_at     timestamptz,
  admin_notes        text,

  requested_at       timestamptz,
  decided_at         timestamptz,
  decided_by         uuid references profiles(id),

  created_at         timestamptz not null default now(),
  updated_at         timestamptz not null default now()
);

comment on table creator_capital is
  'Creator Capital eligibility, review and repayment state. AirPay is the '
  'lender and makes the credit decision; this table records that decision '
  'and the manual workflow around it. No disbursement or collection logic '
  'lives here.';

create unique index if not exists creator_capital_one_open
  on creator_capital (creator_id)
  where status in ('under_review', 'approved', 'active');

create index if not exists creator_capital_creator_idx on creator_capital (creator_id);
create index if not exists creator_capital_status_idx on creator_capital (status);

alter table creator_capital enable row level security;
revoke all on table creator_capital from anon, authenticated, public;

drop policy if exists creator_capital_own_read on creator_capital;
create policy creator_capital_own_read on creator_capital
  for select using (creator_id = auth.uid() or auth_role() = 'admin');

-- No creator INSERT/UPDATE/DELETE policy is granted here on purpose: every
-- write, including "request review", goes through server routes running as
-- the service role, exactly like `withdrawals` and `creator_applications`
-- today (no client-side RLS write path exists for either of those either).
```

If it doesn't, set `updated_at = now()` explicitly in every UPDATE in the routes below, matching `settings.js:44` and `admin.routes.js:801,943`, rather than introducing a new pattern for one table.*

#### 2. Months-of-verified-earnings derivation

Real tables from migrations 001/016: `earnings(creator_id, gross_tzs, creator_tzs, platform_tzs, source, created_at, purchase_id)` and `purchases(user_id, video_id, amount_tzs, creator_amount_tzs, purchased_at, status)`. "Verified earnings" means settled, ledger-recorded money (`earnings`, only ever written inside the settlement transaction), not raw video views.

```sql
-- Distinct calendar months with at least one settled earning, most recent first.
-- "6 months" means 6 distinct months with activity, not necessarily consecutive —
-- a gap should not silently reset progress, since the money already earned is
-- not in question.
select count(distinct date_trunc('month', e.created_at))::int as months_with_earnings,
       coalesce(sum(e.creator_tzs), 0)::int                   as lifetime_creator_tzs,
       coalesce(sum(e.creator_tzs) filter (
         where e.created_at >= now() - interval '90 days'
       ), 0)::int                                             as recent_90d_creator_tzs
from earnings e
where e.creator_id = $1;

-- Paying viewers / refund rate — from purchases, the actual entitlement table:
select
  count(distinct p.user_id)::int as paying_viewers,
  round(100.0 * count(*) filter (where p.status = 'refunded')
        / greatest(count(*), 1), 1) as refund_rate_pct
from purchases p
join videos v on v.id = p.video_id
where v.creator_id = $1;

-- Repeat buyers (a viewer who bought more than one of this creator's videos):
select count(*)::int as repeat_buyers
from (
  select p.user_id
  from purchases p
  join videos v on v.id = p.video_id
  where v.creator_id = $1
  group by p.user_id
  having count(*) > 1
) repeat;
```

## ISSUE 11 — Release model (NEW): Permanent Paid / Premiere→Free+Ads / Exclusive-Premium; MTONYO+ Original flag

### Current state

**Cron + expiry function, both found:**
- Schedule: `server/src/jobs/scheduler.js:70-83` — `{ name: 'premiere-expiry', schedule: '0 2 * * *', run: () => runPremiereExpiry() }`. Daily at 02:00 UTC.
- Batch expiry: `runPremiereExpiry()` — `server/src/jobs/premiere.js:81-113`. Selects up to 500 due videos (`access_type = 'paid_premiere' and is_published = true and deleted_at is null and premiere_ends_at <= now()`), calls `switchOne()` per row.

**No `release_model`/`monetization` column exists today** — confirmed by exact-string grep (`is_original`, `isOriginal`, `release_model`, `releaseModel`: 0 hits repo-wide). The only field governing this is `videos.access_type`, an enum with exactly three values (`001_core_schema.sql:25`): `create type access_type as enum ('ppv_forever', 'paid_premiere', 'free_with_ads')`. Supporting columns: `premiere_days`, `premiere_ends_at`, `ads_enabled`, `premiere_started_at`. The homepage `client/src/components/landing/AccessModels.jsx:42-79` already documents two of the three requested models to visitors: `ppv_forever` ≈ `permanent_paid`, `paid_premiere` ≈ `premiere_to_free`. **`exclusive` (paid/free/unavailable, admin-controlled) has no existing analogue** and is genuinely new.

### Design

#### `release_model` column — migration `035_release_model_and_original.sql`

Ordering: independent of Issue 10's `034_creator_capital.sql` in content, but should be numbered after whatever 034 actually lands as, purely to avoid a numbering collision — no functional coupling between the two.

```sql
-- ============================================================================
-- 035 · release_model + is_original
--
-- `access_type` already encodes most of this (ppv_forever / paid_premiere /
-- free_with_ads) but conflates "how the paywall behaves" with "does this
-- title ever convert." `release_model` names the release strategy explicitly
-- and gives room for `exclusive` without overloading access_type further.
-- `is_original` is a separate, orthogonal, admin-only editorial flag: it
-- affects nothing about entitlement or the paywall, only labelling.
-- ============================================================================

do $$ begin
  create type release_model as enum ('permanent_paid', 'premiere_to_free', 'exclusive');
exception when duplicate_object then null; end $$;

alter table videos
  add column if not exists release_model release_model,
  add column if not exists is_original   boolean not null default false;

-- Backfill for EXISTING rows, mapped from today's access_type:
--   paid_premiere   -> premiere_to_free   (the only model that ever converts)
--   ppv_forever     -> permanent_paid     (pay once, keep forever — no clock)
--   free_with_ads   -> permanent_paid     (never was paid/premiering; no
--                                          historical signal for `exclusive`,
--                                          since it doesn't exist as a concept
--                                          until this migration)
update videos
   set release_model = case access_type
         when 'paid_premiere' then 'premiere_to_free'::release_model
         else 'permanent_paid'::release_model
       end
 where release_model is null;

alter table videos alter column release_model set not null;
alter table videos alter column release_model set default 'permanent_paid';
```

#### Cron/`expireIfDue` skip condition

Both `isDue()` (`premiere.js:22-26`) and `expireIfDue()`'s fast-path guard (`:70-74`) currently gate on `access_type !== 'paid_premiere'`. Once `release_model` exists, both must also require `release_model === 'premiere_to_free'`:
```js
function isDue(video) {
  if (!video || video.access_type !== 'paid_premiere') return false
  if (video.release_model !== 'premiere_to_free') return false   // NEW
  if (!video.premiere_ends_at) return false
  return new Date(video.premiere_ends_at).getTime() <= Date.now()
}
```
The batch selector in `runPremiereExpiry()` needs `and release_model = 'premiere_to_free'` added too. Given the backfill maps every existing `paid_premiere` row to `premiere_to_free`, this is a no-op for current data but correct going forward once an admin can set a video's model independently.

#### Super Admin controls

Attaches to the existing admin video edit route: `admin.routes.js:441-502` (`PATCH /videos/:id`), which already handles `accessType`/`priceTzs`/`premiereDays`/`adsEnabled`/`featured`. Add `releaseModel`/`isOriginal` to the zod schema and the corresponding `coalesce()` clauses in the `UPDATE`.

UI: `admin/src/components/tabs/VideosTab.jsx` — currently a read-only `Access` column with row actions calling `api.admin.updateVideo(v.id, {...})`. Add a `Release Model` select and an `Original` toggle icon-button next to the existing `featured` star toggle. For `exclusive`, a three-way state control (paid/free/unavailable) — simplest consistent addition is a second select shown only when `releaseModel === 'exclusive'`, writing to `accessType`/`priceTzs` (paid ↔ free) plus reusing `is_published = false` for "unavailable" (behaviorally identical to unpublished — not visible, no purchase possible — unless the client wants "unavailable" to be visible-but-not-purchasable, which would need its own boolean).

#### Upload UI exposure

`client/src/components/dashboard/tabs/UploadTab.jsx:91-104` is the creator upload form — creators already choose among `accessType`'s three options, which map to `permanent_paid`/`premiere_to_free` automatically via the backfill logic. **`exclusive` and `is_original` should be admin-only**, not exposed in `UploadTab.jsx` at all — `is_original` is explicitly admin-only per the client's own wording, and `exclusive`'s curated paid/free/unavailable control implies negotiation the self-serve flow isn't meant to support. No changes needed to the upload form; only the admin's `VideosTab.jsx` edit surface can move a video into `exclusive` or flag it `is_original` after the fact.

#### Split for "original" premium videos must read live settings — no hardcoding

Already true today and must **not regress**: the settlement path is `payments.service.js:41-42` — `splitPercentFor(video.creator_id)` then `applySplit(...)`, reading `platform_settings.creator_split_percent` live (with per-creator override), as detailed fully in Issue 1. Nothing about adding `release_model`/`is_original` should introduce a second, parallel split calculation for "Original" or "Exclusive" videos — any future pricing logic for `is_original = true` videos must still resolve through `splitPercentFor()`/`applySplit()`, not a new hardcoded percentage — the same class of bug as the `copy.js` hardcode in Issue 1.

#### Buyers-keep-access is unaffected

Precedent already proven in this repo: M2-VERIFY.md C7 — unpublishing a video through `POST /api/admin/videos/:id/unpublish` was confirmed against production to leave the buyer's `purchases` row and library access untouched. The mechanism is structural: entitlement is decided entirely by `purchases.status = 'active'`, which has no foreign key or dependency on `videos.access_type`/`is_published`/(once added) `release_model`/`is_original`. Changing a video's release model or original-flag after the fact is a plain `UPDATE videos SET ...` with no cascade or application-code path touching `purchases`/`earnings`. The same reasoning that makes unpublish safe for existing buyers applies identically here.
